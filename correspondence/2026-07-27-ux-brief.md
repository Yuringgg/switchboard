# UX/UI Brief — Switchboard console

*From the supervisor/architect to a console-focused build session. 2026-07-27.*

**Read `AGENTS.md` first, then `docs/02-ARCHITECTURE.md` §6 and §8.** This brief
assumes you have. Phase 1 is functionally complete: real Gmail messages are
ingested and the timeline renders them. What follows is about how it *feels*,
not whether it works.

Scope is `apps/console` only. Do not touch `packages/adapters`, `apps/worker`,
or the ingest routes.

---

## Three problems, already diagnosed — don't re-derive them

### 1. New messages don't appear until you navigate away and back

There is no live update. `src/app/page.tsx` is a server component that fetches
once per request, so the only way to see new mail is a full navigation. The user
found this by clicking to `/channels` and back.

**Build Supabase Realtime on `messages`.** `docs/04-ROADMAP.md` schedules this
for Phase 3 and calls it *"the highest ratio of demo impact to implementation
cost in the whole project"* — it is being pulled forward deliberately. Update
the roadmap to reflect that when you're done.

One design decision is yours, and it's real: a Realtime `INSERT` payload
contains the `messages` row **only** — no joined sender, because the timeline
gets the display name through a PostgREST FK embed on `contact_identities`.
So either:

- **(a)** subscribe, then fetch the sender for each new row before rendering it, or
- **(b)** subscribe, and surface a *"3 new messages"* pill that calls
  `router.refresh()` when clicked.

(b) is less code, never renders a half-populated row, and is the pattern most
mail clients actually use. (a) is the more impressive demo. Pick one, and say
which and why — don't build both.

⚠ **Realtime must use the authenticated client** (`lib/supabase/client`), so RLS
scopes the subscription to the signed-in user. Enabling Realtime on a table
means adding it to the `supabase_realtime` publication — that is a schema
change, so it goes in a **hand-written SQL migration** (`0005_…`). Read ADR-012
before you reach for `drizzle-kit`; running `generate` on this project once
proposed dropping RLS on all ten tables.

### 2. The page is slow — and it's a request waterfall, not slow queries

The database is not the problem. `messages_owner_sent_idx` on
`(owner_id, sent_at DESC)` already exists and the corpus is tiny.

The problem is how many sequential round trips happen to Singapore before any
HTML streams:

| # | Where | Call |
|---|---|---|
| 1 | `page.tsx` | `supabase.auth.getUser()` |
| 2 | `page.tsx` | `fetchTimeline()` + `channels` — these two *are* parallel |
| 3 | `AppShell` | `createClient()` + **a second `channels` query** |
| 4 | `src/proxy.ts` | the middleware's own session check, before any of the above |

`AppShell` renders only after `page.tsx`'s awaits resolve, so step 3 is
sequential — and it re-fetches `channels`, which `page.tsx` already has in hand.
Nothing streams; the user waits for every hop before seeing anything.

**What to do:**

- **Fetch `channels` once** and pass it into `AppShell` as a prop. It is already
  being fetched in `page.tsx`.
- **Stop calling `auth.getUser()` more times than necessary per request.** It is
  a network call to Supabase Auth, not a cookie read. Keep the defence-in-depth
  check in `page.tsx` — the comment there explains why it exists and it should
  stay — but don't repeat the work inside `AppShell`.
- **Stream.** Render the shell immediately and put the message list behind
  `<Suspense>` with a skeleton. The frame appearing instantly changes the
  perceived speed far more than shaving milliseconds off the query.
- Measure before and after, and report the numbers. "Feels faster" is not a
  result.

### 3. The sidebar scrolls away with the content

`src/components/app-shell.tsx`:

```tsx
<div className="flex min-h-dvh flex-col md:flex-row">
  <aside className="flex shrink-0 flex-col border-b border-border md:w-60 …">
```

`min-h-dvh` on a flex row with no height constraint means the **document**
scrolls as a single column, so the sidebar rides up with the timeline. As
messages accumulate the aside grows to full document height, and `mt-auto` on
the channel legend pushes it to the bottom of *that* — which is why "Gmail —
Connected" and "Sign out" end up floating in the middle of the page.

**Wanted:** the sidebar and the page header stay put; only the message column
scrolls. Roughly `h-dvh` + `overflow-hidden` on the outer container, the aside
`sticky`/fixed with its own overflow, and the main column owning the scroll.

⚠ Keep the mobile behaviour. The current layout is deliberately CSS-only with no
drawer state — on narrow widths the sidebar becomes a horizontally scrollable
strip above the content. That was a considered choice; don't replace it with a
hamburger and client-side state without saying why.

## Constraints that must not break

1. **No `service_role` in the console outside `app/api/webhooks/`.** ADR-013,
   enforced by `test/service-client-boundary.test.ts`. Realtime uses the user's
   session so RLS applies. This is the security boundary of a multi-tenant
   system, not a style preference.
2. **No direction filter on the timeline.** The demo email is one the user sends
   themselves, so it is `outbound`. Filtering to inbound hides the single
   message the milestone depends on. The reasoning is in a comment at the query
   site — leave it there.
3. **The two empty states stay distinct.** "Waiting for messages" (a channel is
   connected) versus "No messages yet" + a Connect action (none is). A screen
   that looks identical whether the pipeline works or nothing is plugged in cost
   this project a full debugging session. Do not collapse them.
4. **Migrations are hand-written SQL.** ADR-012. Never run `drizzle-kit
   generate` or `drizzle-kit migrate`.
5. **Never log or render message bodies outside the timeline itself.** This is
   real private mail. `docs/02-ARCHITECTURE.md` §6.
6. **Don't scope-creep into Phase 3.** Search, filters, contact pages and
   virtualized infinite scroll are all planned and all out of scope here.
   Realtime is being pulled forward on purpose; nothing else is.

## Done when

- A new email appears in the timeline **without a refresh**, within the 10-second
  budget in `docs/01-PRODUCT-SPEC.md` §7.
- The sidebar and header stay fixed at any message count; only the list scrolls.
- The shell renders before the messages do, and the waterfall above is measurably
  shorter — with before/after numbers.
- `pnpm check` green, CI green including `next build`.
- `docs/04-ROADMAP.md` records that Realtime moved from Phase 3 into Phase 1.
